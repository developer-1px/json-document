# UI Builder 도메인·페이지 UT

2026-10-13, 로컬 Chrome과 실제 UI 디자인 도우미를 사용한 단일 운영자 탐색 실험이다.
일반 사용자 모집 UT나 디자인 품질의 보편적 검증을 대신하지 않는다.
실행 작업 경로는 `json-document-ui-builder`, 미리보기 origin은 `http://127.0.0.1:5184`였다.

## 데이터와 과업

| 도메인 | MOCK 차이 | 사용자 과업 |
| --- | --- | --- |
| 업무 브리핑 | 업무 3건, 업무별 요약·처리 방향·결과 | 선택 → MOCK 실행 → 결과 확인 → 완료 |
| 고객 문의 | 접수/처리 중/해결, 긴 제목, 빈 답변 | 문의 선택 → 상태 변경·답변 작성 |
| 상품 재고 | 수량 0/7/128, 원화 단가, 긴 이름, 빈 메모 | 상품 선택 → 수량·단가 확인·입고 메모 작성 |

`?example=briefing`, `?example=support`, `?example=inventory`는 문서와 대화를
서로 다른 로컬 키에 보관한다. 지원·재고 초기 fixture는 데이터만 제공하고 에이전트가
등록 컴포넌트·바인딩·자동 흐름으로 화면을 조립했다. 기존 사용자 문서는 덮어쓰지 않는다.

## 직접 확인한 동작

- 고객 문의 목록 선택, 상태를 `처리 중`으로 변경, 답변 입력.
- 다른 문의를 선택한 뒤 돌아왔을 때 해당 문의의 상태·답변 유지.
- 새로고침 후 문의 상태·답변의 로컬 복원.
- 페이지 팝오버에서 `문의 요약` 새 페이지 생성, 기존 문의 화면 보존, 빈 새 작업면.
- 에이전트가 문의 총 건수 `3`을 실제 count 바인딩으로 표시.
- 브리핑 결과 페이지에서 홈 복귀 링크 1방향 동작 확인.
- 페이지 이동 컴포넌트 수동 추가와 이동 목적지 선택 UI 열기.
- 재고 재생성 뒤 상품 목록 1개, 수량 `0`, 단가 `59000`, 명확한 개/원 단위,
  입고 메모의 현재 데이터 표시를 DOM에서 확인.

## 미확인과 남은 공백

Chrome 연결이 `Browser is not available: 1`로 끊겼다. 1회 재확인에서도 실패했다.
다른 Chrome 연결/프로필로 전환하지 않았다. 이후 fixture·문서 작업과 집중 진단은
계속했으나 브라우저 검증으로 보고하지 않는다.

- 두 페이지 왕복 전체 흐름, 결과 생성·완료 처리, 새로고침 뒤 전체 페이지 복원.
- 재고 메모 편집 후 다른 상품 왕복·새로고침, 빈 메모와 수량 7/128의 최종 화면 확인.
- 좁은 화면에서 목록/상세 및 페이지 이동, 키보드 포커스 이동.
- 여러 필드가 같은 행에 남는 비교표, 목록 검색·필터, 읽기 전용 값의 일관된 라벨/단위 표현.
- 단일 과업 생성의 성공률: 이번 실험에서는 구체적 복구 요청이 여러 번 필요했다.

따라서 세 도메인에서 공통 토큰을 사용한다는 사실과, 도메인에 맞는 정보 구조·실행 품질이
자동으로 보장된다는 주장은 구분해야 한다. 프롬프트 개선은 실제 API 사용 실패를 줄이는 데
유효했지만 카탈로그의 표현·동작 공백을 대신하지 못했다.

## 지침·스킬 반영

`content-first-ui`에 과업별 결정 기준, 표현/조합/동작 공백의 구분, 실제 capability 확인,
스킬 입출력 계약, 레코드 관계 보존, 0/빈 값·긴 문자열 MOCK 비교를 보강했다.
빌더 읽기·연결·배치 도구에도 같은 판단을 전달했다. 한 사례의 레이아웃이나 카드 사용을
모든 도메인의 고정 템플릿으로 만들지 않았다.

## 전체 등록 후속 — 2026-10-14

공개 시각 API 누락을 조사하고 빌더를 13종에서 88종으로 확장했다. 콘텐츠·입력·조합·날짜·상태
범주를 수동 팔레트와 에이전트에 공유하며, 승인된 props·내부 자식·다중 필드 컬렉션을 연결한다.
레코드 목록은 여러 필드를 한 항목에 묶고 상세 필드 목록은 선택 레코드를 표시한다.
표의 검색·필터·정렬·셀 입력은 Database 정본을 사용한다. 애니메이션 31종은 실제 공개 API를
사용하며 indeterminate 표현에 가짜 진행률을 넣지 않는다.

새 문서/예제는 고유 project ID, 페이지 이동은 page ID를 URL에 사용한다. 기존 보관본과
대화 키는 보존하고 새 문서마다 로컬 저장·대화를 분리한다. 공유 URL 자체는 데이터 업로드가 아니다.

집중 진단: 공개 visual export coverage, 유효 기본값·속성 거부, 조합 순환·복제·삭제·undo,
검색 후 행 ID·숨긴 행 보존, 숫자·기간 입력, 88종 실제 renderer Usage, 새 문서/페이지 링크를 확인했다.
모듈 source API 연결의 제한된 TypeScript 진단은 오류 0건이었다. 전체 build/typecheck/CI는 실행하지 않았다.
전체 Usage 렌더 테스트는 동시 진단 부하에서 기본 5초 제한을 초과했으며, 88종 렌더 목적에 맞춰
30초 제한으로 재실행해 통과했다. 브라우저 연결이 끊긴 이후의 실제 클릭·좁은 화면 UT는 미확인이다.


## Atlas 이슈 관리 — 2026-10-14

`example=issues`는 이슈 내용의 읽기·편집에 집중한 로컬 합성 프로젝트다.
열림/닫힘, 미배정, 빈 마일스톤, 긴 제목과 재현 절차를 포함한 6건을 제공한다.
첫 페이지는 제목 중심 레코드 피드와 선택한 이슈의 본문·속성 편집이며,
둘째 페이지는 동일 데이터의 편집 가능한 표다. 검색·상태 필터와 실제 페이지 이동을 연결한다.
변경은 기존 IndexedDB 문서 저장을 사용하고 독립 project ID로 기존 문서를 보존한다.

콘텐츠 매핑: 이슈 제목 → heading/feed 주정보, 번호 → caption,
본문 → bound textarea, 상태·담당자 → bound select,
라벨·마일스톤 → bound input, 작성자·등록일 → detail-list,
여러 이슈의 속성 비교 → editable table. 모두 공개 Builder API와 등록 렌더러를 소비한다.

진단에서 검색 결과와 상세 선택의 불일치를 확인해, 쿼리 변경 시 보이는 첫 레코드로
선택을 복귀시키고 결과가 없으면 상세 값과 편집을 비운다. 비어 있는 레코드 목록은
기존 콘텐츠 상태 문구로 표시한다. 라벨은 텍스트이며 다중 선택 태그로 가장하지 않는다.
이번 범위는 목록·상세 편집이며 새 이슈 작성과 댓글 타임라인은 추가 과업으로 남는다.
Chrome 연결이 `Browser is not available: 1`로 실패해 시각적·키보드 UT는 미실행이다.

집중 검증 명령: `vitest run --config vitest.config.ts site/tests/unit/issue-workbench.test.tsx`
(3개 통과: 필드 선택·편집·JSON 복원, 실제 등록 렌더러·쿼리, 런타임 DOM 검색·빈 결과·상태 필터·페이지 왕복).
관련 `ui-builder-registration.test.ts` 4개와 `ui-builder-binding-runtime.test.ts` 6개도 통과했다.
변경 API 대상 TypeScript 진단 오류 0건이며 전체 검증 명령을 대신한 결과로 해석하지 않는다.

## 업무 피드의 실제 Chrome 확인

`example=issue-feed` 저장 문서에서 검색 결과 없음의 액션 비활성화, 빈 날짜·상태,
목록 선택과 상세 연결, 결과 페이지 왕복 뒤 선택 유지를 확인했다.
실행에서 화면 편집으로 전환한 16개 root의 내용과 크기는 동일했다.
Shift로 검색과 상태 필터 두 요소를 선택하면 Canvas가 둘 다 pressed로 표시한다.
스크롤된 화면의 재현에서는 scrollTop 462와 첫 요소 y -358이 전환 전후 유지됐다.
앞선 관찰의 일괄 y 변화 78.5px는 이 재현으로 설명되지 않으므로 원인 미확정으로 남긴다.
이 확인은 평면 root 화면에 한정되며 중첩 조합의 편집 좌표를 증명하지 않는다.

중첩 group의 부모·자식을 Space / Shift+Space로 선택한 뒤 실제 Chrome 좌표
드래그 40px을 수행했다. 부모 HTML, 자식 HTML, 자식 Canvas hit 영역 모두
동일하게 x 32→72, y 567.78125→607.78125로 이동하고 Undo 한 번으로 복구됐다.
3단계 shell toolbar slot→group→leaf의 명령 이동은 각 객체에 한 번 반영되고
무관한 객체는 보존되는 집중 회귀 테스트로 검증한다. 이 기록은 포인터를 놓은
뒤 결과 검증이며 드래그 도중 프레임별 preview 측정을 대신하지 않는다.

업무 피드에서 금요일 검색 → 디자인 → AI 반영 → 미리보기 → 디자인을 실행했다.
AI 완료 후 검색값 금요일, 선택 업무 TEAM-102, 한 행 목록이 유지됐다.
다시 디자인으로 전환한 16개 root의 텍스트·x·y·width·height 차이는 0개였다.
데이터 탭 왕복 뒤에도 같은 검색과 목록을 확인했다. 확인 범위는 이 저장 문서의
해당 선택 상태이며 다른 도메인이나 모든 중첩 조합을 증명하지 않는다.

속성 조작 조합 실험에서 생성 AI는 Toolbar의 가로 규칙이 카탈로그에 없다고
거부했다. 실제 구현의 flex row·줄바꿈·간격을 related-controls recipe에 등록한
뒤 같은 요청이 기존 상태·마감일을 한 그룹으로 연결했다. DOM에서 각 컨트롤
한 개씩이며 x 위치가 순차 배치되는 것을 관찰했다. AI의 최상위 흐름 정리는
관찰 시점에 진행 중이므로 최종 배치와 동작 확인은 별도다. 새 issue-feed fixture도
정본 toolbar.childIds 조합을 사용하며 저장된 사용자 문서를 덮어쓰지 않는다.

속성 조작 그룹의 상태 변경은 목록에 반영되고 달력 날짜 선택은 레코드 왕복
후 유지됐다. 검증용 상태·날짜는 원래 값으로 되돌렸다. 그룹 조합 후 디자인
전환에서 자식을 포함한 17개 HTML 영역의 내용·좌표·크기 차이가 없었다.
직접 날짜 입력에서는 DOM draft와 저장값 불일치를 관찰해 HtmlDateField commit이
blur/Enter 이벤트의 실제 input value를 읽도록 수정했다. 직접 입력 경로의 추가
브라우저 확인과 속성 그룹을 메모 앞에 놓는 AI 순서 수정은 별도로 진행한다.

40px 드래그를 수행했다. 상태·마감일 모두 한 번 이동하며 Undo 한 번으로 원복됐다.
